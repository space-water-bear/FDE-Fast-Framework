# FDE 客户现场开发与交付评估

评估日期为 2026 年 11 月 11 日。GitHub `main` 的代码合并提交为 `d7409a711ee00b96776bcb58c9fdbb2516031b02`，与复测候选 `5fe0aef22b639fd5085775614706f317fda29125` 的源码树一致。P0/P1 开发交付链和机器人、图表、生成技能已在同一基线。[合并 PR #1](https://github.com/space-water-bear/FDE-Fast-Framework/pull/1)

**可以用来做现场试点。** 在依赖已准备、实施人员参与审阅的条件下，当前版本具备用内置智能体新建基本字段业务模块、修复本次生成代码、运行检查、打包并完成 Linux/SQLite 首次安装的流程。完整的持续交付仍缺两段实证。第一段是把真实模型接入这条内置流程完成业务验收。第二段是对已有模块进行跨任务修改，并把有业务数据的 V1 升级为 V2。

## 需求覆盖

| 现场环节 | 当前能力 | 验收边界 |
| --- | --- | --- |
| 从需求生成业务 | 开发工作台从已提交模板创建客户项目，任务使用独立工作区。内置智能体通过固定工具生成模型、服务、接口、页面、表单和业务安装资产。 | 本轮以单表维修登记验收。自动生成范围是基本字段和常规 CRUD。复杂审批、跨表事务、关系和字典联动需要单独设计与验证。 |
| 增量修改 | 智能体可以按文件哈希修改本任务新增的业务源码，检查失败后可在预算内修复。 | 基线文件受保护。后续任务仍从项目原基线出发，成功候选目前没有基线提升流程。 |
| 自动测试 | 固定 Docker Runner 运行 Go、Node、类型检查和构建等 12 项检查。任务成功要求实际检查通过，且报告与当前源码哈希匹配。 | 本轮另做了业务 HTTP 检查。真实客户的业务规则、数据规模和验收用例需要随需求补充。 |
| 发布与首次安装 | 人工审阅差异后构建发布包，按明确的版本和目标部署。发布清单绑定已检查源码和构建制品。 | 本轮目标为本机 Docker Linux/arm64 和独立 SQLite。安装器支持离线布置已构建的包，首次准备检查镜像和下载依赖需要网络。 |
| 运行与后续升级 | 显式 `bootstrap` 初始化数据库，`verify` 和 `serve` 检查已安装版本。本轮验证了同版本重启后数据保留。 | 首次安装流程会拒绝在同一目标上安装不同版本。带数据升级、迁移失败恢复、版本回退和客户目标环境仍待验收。 |

## 真实模型证据

11 月 6 日另有一轮真实模型试验。项目普通聊天入口调用 `deepseek-flash` 四次，使用三项技能生成复杂维修工单的六个文件。前后端各经一轮同模型修复，之后通过七组 HTTP 检查和十五项浏览器检查。验证覆盖状态流转、归属隔离、并发版本控制和图表汇总，独立测试库重启后保留五条记录。

这轮试验由外部受限脚本负责落盘、测试编排和验收。它证明了框架的模型入口和技能可以支撑更复杂的业务代码生成。当前内置交付链的复测使用脚本网关。将真实模型、内置工作台与客户部署目标放在同一次验收中，仍是现场试点的待完成项。原始模型输出和验收附件保留在本机。

## 下一轮验收

1. **真实模型走完内置链。** 用维修工单作为固定需求，从合并后的 `main` 创建项目。真实模型经工作台生成、修复并通过独立业务测试，实施人员审阅差异并构建 V1。记录实际工具调用、检查、源码和发布清单的关联。
2. **用已录入数据的 V1 验证 P2。** 审阅后提升项目基线。发起第二个任务，为已安装模块新增字段与一条状态规则。验证旧工单、原有权限和人工源码保留，校验重试及迁移失败恢复，再对同一个目标完成 V2 升级和回退演练。
3. **确认客户环境。** 在约定的架构、数据库和网络条件下使用已验证的发布包，分别记录应用 readiness、业务操作、重启和客户验收结果。
